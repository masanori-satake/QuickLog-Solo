# ROADMAP: メンテナンスコスト低減ロードマップ

QuickLog-Solo を「10年後も同じように動作・保守できる」状態に近づけるため、メンテナンス負荷を下げる方向のアイディアを列挙する。本ドキュメントは検討用のアイディアリストであり、実行順や採否を確定するものではない。各項目には想定効果と、コア・フィロソフィー（持続可能性・ミニマリズム・透明性・長期保守性）との整合を添える。

> 注意: 本リストは提案の集約であり、着手前に個別に `docs/spec.md` との整合と影響範囲の確認が必要。実装を伴う項目は `projects/app/` または `shared/` に触れるためバージョンバンプ対象になりうる。

## 現状のメンテナンス負荷の実測サマリ

規模の可視化のため、セッション時点での実測値を記録する（概算・行数はコメント含む）。

| 領域 | ファイル数 | 行数(概算) | 備考 |
|------|-----------|-----------|------|
| `shared/` | 96 | 約24,500 | うち `shared/js/animation` に45モジュール |
| `projects/app` | 16 | 約9,680 | `app.js` 単体で3,472行 |
| `projects/studio`（Animation Studio） | 9 | 約3,411 | エディタ |
| `projects/category-editor` | 7 | 約3,080 | エディタ |
| `projects/alarm-editor` | 8 | 約1,638 | エディタ |
| `projects/animation-maker` | 5 | 約3,814 | `maker.js` 2,113行 |
| `projects/web`（LP・ガイド） | 8 | 約2,931 | GitHub Pages デプロイ |
| `scripts/`（ビルド・検証） | 17 | 約1,345 | Python 14 + Node 2 + 共通 |
| `tests/`（E2E ほか） | 56 | 約9,420 | Jest + Playwright |

メンテナンス負荷が集中しているのは主に次の4点と考えられる。

1. **サブプロジェクトの多さ**（アプリ本体 + エディタ4種 + Web）。各々に HTML/CSS/JS と `shared` シンボリックリンクの管理が発生する。なお、コア保守対象の優先順位はユーザー確認済み（下記 A 参照）。
2. **`app.js` の肥大化**（3,472行）と `maker.js`（2,113行）の巨大単一ファイル。
3. **背景アニメーション基盤の重量**（45モジュール + Worker + レジストリ自動生成 + 整合性検証 + 品質評価テスト）。
4. **ビルド/検証パイプラインの本数**（Pythonスクリプト14本、CI 9本、pre-commit、独自ポリシー検証）。

以下、負荷源ごとに削減アイディアを列挙する。

## A. サブプロジェクト構成の整理（最も効果が大きい領域）

サブプロジェクトの位置づけはユーザー確認により以下に確定している。この優先順位に沿って整理する。

| サブプロジェクト | 位置づけ | 方針の方向性 |
|------------------|----------|--------------|
| **category-editor** | 必須（不可欠） | コア保守対象として維持 |
| **alarm-editor** | 必須（不可欠） | コア保守対象として維持 |
| **animation-maker** | 次点（魅力提供） | 維持するが整理・軽量化の対象 |
| **studio** | 任意（学習教材、使われない可能性が最も高い） | 分離・アーカイブの第一候補 |

- **A-1.（第一候補）studio を分離・アーカイブする。** 学習教材的な位置づけで日常利用が想定されず、約3,411行（`studio.js` 735行 + `studio.css` 1,454行 ほか）と CSS 中心にそれなりの重量がある。別リポジトリ化またはアーカイブし、CI・lint・テスト・`shared` リンク管理の対象から外して本体保守を軽くする。**削減効果が最も大きく、思想的リスクが最も小さい第一歩。**
- **A-2. animation-maker は「魅力機能」として維持しつつ軽量化する。** 廃止せず残す前提で、`maker.js`(2,113行) を描画・入出力・UI に分割し（B-3 と連動）、studio 廃止後に studio と重複していた責務があれば animation-maker 側へ一本化する。studio を残さないため、A の初版にあった「studio との統合」案は不要。
- **A-3. category-editor / alarm-editor はコア保守対象として明示的に維持する。** 必須のため削除・分離はしない。ただし `shared` への依存と重複コードの整理（B・E）は本体同様に適用し、保守品質を保つ。
- **A-4. エディタ群を「配布物」と「開発時ツール」で分類する。** 必須2種 + animation-maker を残す前提で、拡張機能ZIPに同梱するものと開発時のみ使うものを整理する。studio 分離後、残るツールの CI・lint・テスト範囲を見直して本体検証を軽くする。
- **A-5. `projects/web`（LP・ガイド）を別リポジトリ/別デプロイに切り出す。** アプリ本体とライフサイクルが異なる（GitHub Pages デプロイ、`deploy-pages.yml`）。分離すればアプリ側CIから Pages 関連ワークフローを外せる。
- **A-6. `shared` へのシンボリックリンク運用を見直す。** 各サブプロジェクト直下の `shared` リンクは環境依存（Windows/クローン時）でつまずきやすい。studio 分離・Web分離でリンク管理箇所が減る。

## A′. 移設戦略: API仕様を境界にした疎結合化（確定方針）

studio は**別リポジトリへ移設**する（アーカイブ削除ではない）。狙いは QuickLog-Solo リポジトリを可能な限りコンパクトに保ち、ワークフローを単純化し、ビルドを最短時間で完了させること。

### ストーリー（設計の骨子）

- QuickLog-Solo 本体には、**アニメーションモジュールのAPI仕様（契約）だけ**を正典として残す。
- studio（将来的にはエディタ系全般）は、そのAPI仕様に準拠したモジュールを編集する「**準拠エディタ**」として外部の別リポジトリで管理する。
- 本体とエディタは**API仕様というコントラクトのみで結合**する。実装は互いに独立して進化できる。これは「安定した契約に依存し、揮発しやすい実装には依存しない」という長期保守性の観点で筋の良い分離。

### 残すもの / 移すものの線引き

| 対象 | 扱い | 理由 |
|------|------|------|
| `docs/animation_module_spec.md`（仕様v2.0） | **本体に残す（正典）** | エディタ・モジュール双方が準拠する契約の Source of Truth |
| `shared/js/animation_base.js`（基底クラス） | **本体に残す** | API仕様の実体。契約の一部 |
| `shared/js/animations.js` / `animation_worker.js` / レジストリ | **本体に残す** | 実行時にモジュールを読み込む本体側ランタイム |
| `shared/js/animation/`（各モジュール実装） | **要判断（C章と連動）** | 同梱する代表モジュールのみ残し、それ以外は移設先で管理する選択肢 |
| `projects/studio/`（エディタ本体） | **別リポジトリへ移設** | 学習教材・準拠エディタ。本体のライフサイクルと分離 |

### 移設の実行方針

- **A′-1. API仕様を「公開契約」として明文化・バージョン管理する。** `docs/animation_module_spec.md` は既に仕様v2.0として存在。これを本体の唯一の正典と位置づけ、破壊的変更時はバージョンを上げる運用を明記する。エディタ側はこの仕様バージョンに追従する。
- **A′-2. 別リポジトリ（例: `QuickLog-Animation-Studio`）を新設し、studio を Git 履歴付きで移設する。** `git subtree split` や `git filter-repo` で `projects/studio/` の履歴を保持したまま切り出す。単純コピーで履歴を捨てる選択肢もあるが、履歴保持を推奨。
- **A′-3. 移設先が本体に依存する部分を「仕様＋最小限の共有ファイル」に絞る。** studio は現状 `shared` リンク経由で本体コードを参照している。移設後は API仕様（`animation_base.js` 等の契約部分）だけをコピーまたは軽量パッケージとして取り込み、本体全体への依存を断つ。
- **A′-4. 本体から studio を削除し、関連する CI・lint・テスト・`shared` リンクを撤去する。** `projects/studio/` 削除に伴い、studio 専用の E2E/スクリーンショットテスト、lint 対象、`shared` シンボリックリンクを本体から外す。これがビルド・ワークフロー短縮の直接効果。
- **A′-5. 相互リンクを整備する。** 本体 README とエディタ側 README に相互リンクを張り、「本体=契約の提供元」「エディタ=契約の準拠ツール」の関係を明示する。仕様バージョンの対応表を置くと追従が楽になる。
- **A′-6. animation-maker の扱いを段階的に決める。** animation-maker は当面本体に残す（次点・魅力機能）。studio 移設で「別リポジトリ＝準拠エディタ」の型が確立したら、将来的に同じ型で animation-maker も移設する余地を残す（YAGNI に配慮し、いま同時には動かさない）。

### 期待効果

- リポジトリの行数・ファイル数が減り、クローン・CI・ビルドが軽くなる。
- 本体の関心事が「記録ツール + アニメーション実行 + API仕様の提供」に絞られる。
- エディタは本体のリリースサイクルに縛られず独立して改善できる。

## B. `app.js` / 巨大ファイルの分割と単純化

- **B-1. `app.js`(3,472行) を責務単位のESモジュールに分割する。** タイマー制御・履歴UI・設定UI・日報コピー・アラームUI などをファイル分割。Vanilla JS + ES Modules のまま実施できる（フレームワーク不要）。
- **B-2. UI層とロジック層の境界を再徹底する。** `app.js` に紛れ込んだ計算・整形ロジックを `shared/js/logic.js` 側へ寄せ、`app.js` は「高レベル関数の呼び出し」に徹する（AGENTS.md の SLAP 原則）。テスト容易性が上がり回帰が減る。
- **B-3. `maker.js`(2,113行) の分割、またはA-2で廃止。** 統合しない場合でも、描画・入出力・UIに分割する。
- **B-4. デッドコード・未使用エクスポートの棚卸し。** `no-unused-vars` は有効だが、モジュール横断の未使用は残りやすい。定期的な棚卸しで表面積を縮小する。

## C. 背景アニメーション基盤のスリム化

- **C-1. アニメーションモジュール45種の絞り込み。** 本体には代表的な数種の同梱モジュールと **API仕様の正典（`docs/animation_module_spec.md` / `animation_base.js`）を残す**（A′章）。それ以外のモジュールは、準拠エディタと同じ別リポジトリ側での管理へ移す選択肢を検討する。モジュール数減 = レジストリ生成・整合性検証・評価テストの対象減。
- **C-2. アニメーション品質評価テスト（`test:animation-eval`）の運用軽量化。** 常時CI実行から、変更時のみ/手動実行へ切り替えることでCI時間と保守を削減。
- **C-3. レジストリ自動生成（`generate_animation_registry.py`）と整合性検証（`verify_animations.py`）の統合。** 2スクリプトを1つにまとめ、`test`/`test:e2e` の前処理を単純化する。
- **C-4. 背景アニメーション機能自体をオプトイン（既定オフ）にする。** ミニマリズムの観点でコア体験から外し、将来的にコア保守対象から切り離す布石にする。
- **C-5. Web Worker + BroadcastChannel の同期経路（`anim_sync.js` / `session_sync.js` 860行）の見直し。** アニメーション廃止・縮小に伴い不要になる同期ロジックを削減する。

## D. ビルド・検証パイプラインの簡素化

- **D-1. Python依存の削減。** 検証スクリプト14本がPython。技術スタックはVanilla JS中心なので、可能なものはNodeスクリプトへ寄せ、実行系を1つ（Node）に統一するとCI環境構築・保守が単純になる。
- **D-2. CIワークフロー9本の統合。** code-quality / coverage / e2e / security-scan / version-bump などをジョブ単位で1〜2ファイルに集約し、重複するセットアップ（チェックアウト・依存インストール）を共通化する。
- **D-3. 独自ポリシー検証スクリプトの取捨選択。** `verify_project_policies.py` / `check_root_files.py` / `audit_localization_mixing.py` / `language_check.py` などは価値がある一方で保守対象。ESLint/Stylelint のカスタムルールや既存Lintに寄せられるものは寄せ、独自スクリプトの本数を減らす。
- **D-4. `build`（アイコン生成・レジストリ生成・バージョン確認・ZIP・Viteビルド）の工程削減。** PNGアイコン生成をコミット済みアセット化する、Viteビルドの要否を再確認する（本番バンドル不要の方針との整合）など、ビルド手数を減らす。
- **D-5. バージョンバンプ強制ルールの運用簡素化。** `verify_version_impact.py` によるバンプ漏れ検出はコミット規約に依存する。Conventional Commits + 自動バンプ（リリース時一括）に寄せ、日々の手間を減らす選択肢を検討する。
- **D-6. pre-commit と CI の役割重複を整理する。** 同じチェックを二重に走らせている箇所を洗い出し、pre-commitは高速チェックのみ・CIは網羅チェックのみに役割分担する。

## E. テストの整理

- **E-1. テスト56ファイル/9,420行の重複・低価値テストの棚卸し。** カバレッジ寄与の低いテストや、実装詳細に密結合して壊れやすいテストを削減する。
- **E-2. E2E（Playwright）とユニット（Jest）の責務再分担。** E2Eで担保している内容のうちユニットで十分なものを移し、遅く壊れやすいE2Eの本数を減らす。
- **E-3. アニメーション関連テストの縮小。** C-1/C-2と連動し、モジュール削減に合わせてテストも削減する。

## F. 国際化（i18n）の負荷軽減

- **F-1. 対応言語数の再評価。** 8言語（en/ja/de/es/fr/pt/ko/zh）は追加文言のたびに9ファイル更新が必要。実利用の少ない言語を「コミュニティ翻訳・ベストエフォート」に格下げし、コア保証はen/jaのみとする選択肢。
- **F-2. 翻訳キーの棚卸しと未使用キー削除。** ロケールファイル間のキー整合を自動チェックし、未使用キーを削減して更新負荷を下げる。
- **F-3. `audit_localization_mixing.py` の役割をLint統合に寄せる（D-3と連動）。**

## G. ドキュメント・設定の集約

- **G-1. ドキュメントの正典を `docs/spec.md` に一本化し続ける。** README_DEV / README_TEST / README_DEPLOY / README_ACTIONS / README_GUIDES など分散ドキュメントの重複を減らし、リンク集約する。
- **G-2. ルート直下の設定ファイルの点検。** `.pr_agent.toml` / `crowdin.yml` など、現在使っていない外部連携設定があれば削除し、認知負荷を下げる（`google-site-verification` 等の所有権確認ファイルは削除禁止）。
- **G-3. AI/エージェント関連ディレクトリ（`.jules` / `.kilo`）の要否確認。** 使っていない補助設定はリポジトリから外す。

## H. 依存関係の維持コスト低減

- **H-1. devDependencies の削減・固定。** 本番依存ゼロは維持しつつ、開発依存（Vite・Playwright・Jest系など）のうち役割が重複するものを整理する。A-4でWeb分離ができればVite依存を外せる可能性がある。
- **H-2. Dependabot / OSVスキャンの対象と頻度の最適化。** 更新PRの洪水を避け、まとめ更新・週次などに調整して対応の手間を平準化する。現状 `dependabot.yml` は npm ecosystem のみ・weekly。`github-actions` ecosystem を追加すると Actions のバージョン固定更新も自動化できる。逆に更新PRが多すぎる場合は `groups` でまとめる。

## I. 一般的な開発/運用コスト低減タスク（実装に基づく横断施策）

プロジェクト固有の整理（A〜H）とは別に、どのプロジェクトにも当てはまる「開発・運用の地力を上げてコストを下げる」施策を、本リポジトリの実装状況に照らして列挙する。

### I-1. 技術的負債の可視化と段階的解消

- **I-1-1. ESLint の除外リスト（技術的負債）を計画的に解消する。** `eslint.config.js` は `shared/js/db.js` `logic.js` `session_sync.js` `background.js` `backup.js`、studio/alarm-editor、animation 一式などを `ignores` に列挙し、コメントで「Phase 1 以降で順次解除予定」と明記済み。**負債が可視化されている良い状態**だが Phase 1 が未着手。除外を1ファイルずつ外して lint を通す小PRを積み重ねると、負債が確実に減る。
- **I-1-2. 除外解除の順序を「移設・削除予定のものは後回し」で決める。** studio は A′ で移設予定、animation は C で絞り込み予定。除外解除の労力を、本体に残る `logic.js` `db.js` など「残すコード」から優先的に投じ、消えるコードには手をかけない。
- **I-1-3. コード内 `TODO` / `FIXME` の棚卸し。** 定期的に grep し、対応・削除・Issue化のいずれかに振り分けて放置TODOを増やさない。

### I-2. フォーマッタ/リンタの一貫適用

- **I-2-1. `npm run format` の対象範囲を全体へ拡大する。** 現状 `format` スクリプトは `variables.css` `storage.js` `eslint.config.js` `utils.js` `schema.js` `i18n.js` など**数ファイルのみを明示指定**している。Prettier 設定は既にあるので、除外ファイルを `.prettierignore` で管理しつつ対象を「全体」に広げると、フォーマット差分による無駄なレビュー往復が減る。
- **I-2-2. 「保存時フォーマット」をエディタ設定として共有する。** `.vscode/settings.json`（`editor.formatOnSave` + Prettier 既定）をコミットし、貢献者全員のフォーマットを揃える。手動 `format` 実行を不要にする。
- **I-2-3. lint/format をワンコマンド化する。** `lint:fix`（eslint --fix + stylelint --fix）を追加し、CI 落ちの事前解消を容易にする。

### I-3. CI/自動化の効率化

- **I-3-1. 外部再利用ワークフロー依存を把握・文書化する。** `code-quality.yml` は外部リポジトリ `masanori-satake/common-workflows/.github/workflows/base-ci.yml@v1` を呼んでいる。DRY で優れる一方、**別リポジトリの変更が本体CIに影響する暗黙依存**。バージョンタグ固定（`@v1`）の運用ルールと、何を共通化しているかを README/docs に明記して、追跡可能にする。
- **I-3-2. CIのキャッシュとパス絞り込みを徹底する。** 既に `paths-ignore`（docs/README）や npm/pip キャッシュ、`concurrency` によるキャンセルは導入済み。E2E は Node+Python+Playwright ブラウザの三重セットアップで重いので、Playwright ブラウザキャッシュの追加や、変更パスに応じた条件実行でさらに短縮できる。
- **I-3-3. `paths` フィルタの一貫性を見直す。** `code-quality.yml` は PR で `projects/** shared/** ...` に絞る一方、`e2e.yml` の PR は全変更で走る。E2E も対象パスを絞れば無駄実行が減る。
- **I-3-4. ジョブのタイムアウトと権限の最小化を全ワークフローに適用する。** e2e は `timeout-minutes: 20` と `permissions: contents: read` を設定済み。同じ規律を9本すべてに適用し、暴走・過剰権限を防ぐ。

### I-4. コミット前チェック（pre-commit）の軽量化

- **I-4-1. pre-commit の重い hook を「push時」または「CI側」へ寄せる。** 現状 local hook で Python 検証7本 + `jest`（`npm test`）が走りうる構成。コミットのたびに全テストが走ると開発体験が重い。**高速チェック（フォーマット・行末・小さなポリシー検証）はpre-commit、テスト・パッケージ生成はCI**へ、と役割を分離する（D-6 と連動）。
- **I-4-2. `create-package` hook のトリガ条件を確認する。** `version.json`/`manifest.*.json` 変更時のみ動く設定になっており妥当。他の重い hook も同様にファイルトリガ化できないか点検する。

### I-5. リリース/バージョニングの自動化

- **I-5-1. CHANGELOG を導入する。** 現状 `CHANGELOG.md` は存在しない。Conventional Commits を採用済みなら、`release.yml` 内で自動生成（commit からの changelog 生成ツール）を組み込むと、リリースノート作成の手間が消える。
- **I-5-2. バージョンバンプの自動化（D-5 と連動）。** 複数ファイル（`package.json`/`version.json`/manifest）へ手動同期している現状を、`bump_version.py` の一括同期は維持しつつ「リリース時に一括バンプ」へ寄せ、日々のバンプ漏れ検出（`verify_version_impact.py`）の負荷を下げる。
- **I-5-3. リリース手順を docs に一本化する。** タグ・ZIP作成・ストア申請・Pagesデプロイの手順を1ページにまとめ、属人化を防ぐ。

### I-6. オンボーディング/開発環境の再現性

- **I-6-1. 開発セットアップを1コマンド化する。** Node(`npm ci`) と Python(`pip install -r requirements.txt`) と Playwright(`npx playwright install`) が必要。`npm run setup` 等でまとめ、新規貢献者・将来の自分の立ち上げコストを下げる。
- **I-6-2. ツールのバージョンを固定・明記する。** CI は Node `lts/*`・Python `3.12`。`.nvmrc` や `.python-version`、`package.json` の `engines` を置いて、ローカルとCIの差異による「自分の環境だけ動かない」を防ぐ。
- **I-6-3. `shared` シンボリックリンクのセットアップを文書化/スクリプト化する。** Windows でのクローン時にリンクが壊れやすい（A-6）。生成手順を README かスクリプトに残す。

### I-7. ドキュメントと知識の集約

- **I-7-1. `docs/spec.md` を唯一の正典として維持し続ける（G-1 と連動）。** 判断の背景（Why）を spec に集約する運用は AGENTS.md にも定義済み。分散した README 群（DEV/TEST/DEPLOY/ACTIONS/GUIDES）は spec への索引に寄せる。
- **I-7-2. 「使っていない設定ファイル」を定期的に棚卸しする。** ルートに `.pr_agent.toml` `crowdin.yml` `.jules` `.kilo` など外部連携・エージェント設定が多い。使っていないものは削除し、認知負荷とセキュリティ面（不要な連携）を減らす（`google-site-verification` 等の所有権確認ファイルは削除禁止）。

### I-8. セキュリティ/コンプライアンスの省力運用

- **I-8-1. 依存脆弱性対応の自動化を維持する。** `security-scan.yml`（OSV）と Dependabot を軸に、本番依存ゼロ方針（`audit_production_dependencies.py`）を CI で守り続ける。**本番依存ゼロは脆弱性対応コストを最小化する最大の武器**なので堅持する。
- **I-8-2. GitHub Actions のバージョン固定（pinning）。** サードパーティ Action は SHA 固定または Dependabot(`github-actions`) 管理にし、サプライチェーンリスクと突然の破壊的更新を防ぐ（I-3-1 / H-2 と連動）。
- **I-8-3. 権限最小化を全ワークフローで徹底（I-3-4 と連動）。** `permissions` を明示し、`security-events: write` 等の強い権限は必要なジョブに限定する。

## 優先度の考え方（目安）

メンテナンスコスト削減の費用対効果が高いと考えられる順の目安。実際の採否はユーザー判断による。

1. **A（サブプロジェクト整理）** — 削減行数・削減工程が最も大きい。まずどのサブプロジェクトを「コア保守対象」に残すかの意思決定から。
2. **C（アニメーション基盤スリム化）** — モジュール数・専用スクリプト・専用テスト・同期ロジックが芋づる式に減る。
3. **D（パイプライン簡素化）** — 日々のCI/コミット体験に直結。
4. **B（`app.js`分割）** — 削除ではなく整理だが、将来の変更コストを継続的に下げる。
5. **I（一般的な開発/運用施策）** — 低コストで着手でき効果が持続するものが多い（フォーマット全体適用、pre-commit軽量化、CHANGELOG、Actions固定など）。A〜Hと並行して少しずつ進められる。
6. **E / F / G / H** — 中〜長期の地道な圧縮。
